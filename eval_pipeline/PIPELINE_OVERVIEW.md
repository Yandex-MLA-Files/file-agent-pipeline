# eval_pipeline — архитектура и метрики

Разовый обзорный документ для команды. Не часть постоянной документации проекта
(README покрывает install/run) — можно удалить после того, как все ознакомятся.

## Что это

`eval_pipeline` — независимый LLM-as-judge оценщик для RAG-ответов. Не привязан
к конкретному RAG-пайплайну или датасету: единственный контракт — таблица с
колонками `id`, `question`, `answer_model`, `contexts`, `answer` (эталон).
Откуда взялись эти четыре колонки — не забота этого пакета.

## Поток данных

```
run-файл (.parquet/.csv)
        │
        ▼
eval/run_loader.py :: load_run()
  — валидирует схему (обязательные колонки, дубликаты id, contexts как
    list[str], непустой answer_model)
        │
        ▼
eval/judge/ragas_judge.py :: RagasJudge.evaluate()
  — прогоняет 5 метрик через ragas.evaluate() на реальном LLM (judge-модель,
    настраивается через JUDGE_BASE_URL/JUDGE_API_KEY/JUDGE_MODEL)
  — попутно пишет два лога (см. "Логи" ниже)
        │
        ▼
eval/report.py :: build_report() → save_report() + append_run_log()
  — агрегирует по каждой метрике (mean/median/min/max, опционально разбивка
    по негативным примерам через --negative-example-pattern)
  — report.json + scored.parquet кладутся в --out (перезаписывается на
    каждый прогон с тем же --out)
  — одна строка добавляется в logs/runs_log.jsonl (не перезаписывается —
    для сравнения прогонов между собой во времени)
```

Точка входа: `scripts/run_eval.py --run <файл> --out <папка>`.

## Логи (`logs/`, в .gitignore, создаются автоматически)

| файл | накопление | что содержит | зачем |
|---|---|---|---|
| `logs/usage_log.jsonl` | одна строка добавляется на каждый `evaluate()` | токены (input/output/cached) и стоимость в рублях | контроль расходов на judge-модель, тренд по времени |
| `logs/judge_trace_log_<timestamp>.jsonl` | **отдельный файл на каждый `evaluate()`**, не дописывается | на каждую строку датасета: `question`, `answer_model`, `reference` (эталон), `contexts`, `verdict` по всем 5 метрикам, полный `reasoning_trace` judge-а | разбор конкретных низких оценок конкретного прогона; формат специально под ручную проверку оценщиками — можно судить о вердикте, не открывая исходный run-файл |
| `logs/runs_log.jsonl` | одна строка добавляется на каждый `evaluate()` | файл, `--out`, judge, средние по метрикам | сравнение прогонов между собой (разные версии RAG, разные промпты) |

**Известное ограничение `judge_trace_log_<timestamp>.jsonl`:** ragas называет промпт
одинаково независимо от направления проверки (например, у `answer_correctness`
одна и та же NLI-проверка используется и для precision, и для recall). Наш лог
берёт трейсы из `result.traces` (готовая структура ragas), которая схлопывает
повторные вызовы одноимённого промпта внутри одной метрики — в логе виден
только последний вызов, не оба направления. Для отладки конкретной метрики
этого обычно достаточно, но это не полная картина всех LLM-вызовов внутри
`evaluate()`.

## Текущее состояние: финальная конфигурация, два прогона для сверки

Конфигурация стабилизировалась (`strictness=1` для `answer_relevancy`,
локальный эмбеддер, языковая инструкция для консистентности, расширенные
`JUDGE_TIMEOUT`/`JUDGE_MAX_RETRIES`). Два независимых полных прогона (81
пример, `answers_run.parquet`) дали близкие числа — воспроизводимость в
пределах обычного шума LLM, ни одного `NaN` ни в одном из них:

| метрика | прогон A | прогон B |
|---|---|---|
| faithfulness | 0.7397 | 0.7587 |
| answer_correctness | 0.3825 | 0.4135 |
| answer_relevancy | 0.6313 | 0.6485 |
| context_precision | 0.6064 | 0.6081 |
| context_recall | 0.7132 | 0.678 |

Стоимость ~500 руб за прогон (`deepseek-v4-flash` через Yandex Cloud AI
Studio, embeddings бесплатны — считаются локально). Формат
`logs/judge_trace_log_<timestamp>.jsonl` последнего прогона готов для
ручной проверки оценщиками (`question`/`answer_model`/`reference`/
`contexts`/`verdict`/`reasoning_trace`, см. таблицу логов ниже).

## Частая ловушка: `contexts` должен быть `list[str]`

`run_loader.py` проверяет только, что `contexts` — list (не dict), но не что
внутри строки. Если туда попадает вывод ретривера как есть (список словарей
`{rank, chunk_id, text, score, metadata_json, ...}`), валидация формально
пройдёт, но ragas ждёt `list[str]` — метрики контекста (`context_precision`,
`context_recall`) сломаются или дадут мусор. Перед подачей в judge контекст
нужно свести к списку строк (взять `text` из каждого чанка).

## Метрики: что означают и как читать число

Все 5 метрик — числа от 0 до 1 (кроме бинарных где отмечено), каждая
проверяется отдельным вызовом judge-модели. Промпты/few-shot примеры —
ragas-дефолты без перевода (были русские переводы 4 из 5 метрик, убрали —
`EXPERIMENT_RU_VS_EN_PROMPTS.md` показал, что разница была в пределах
обычного шума между прогонами, не стоило поддерживать два набора промптов).

**Одно исключение** — `_match_response_language_to_input` в `ragas_judge.py`
добавляет одну фразу в конец инструкции каждого промпта: отвечать на том же
языке, что и вход (вопрос/ответ/контекст). Без этого язык рассуждений в
трейсе был непредсказуем — на одном и том же (полностью русском) прогоне
часть промптов рассуждала по-русски, часть по-английски (проверено на
`judge_trace_log`). Это не перевод промптов (то, что убрали выше) — просто
просьба зеркалить язык входа, поэтому одинаково работает и на русских, и на
английских данных.

- **faithfulness** — насколько ответ подкреплён контекстом (галлюцинации).
  Ответ разбивается на атомарные утверждения, каждое проверяется NLI-моделью
  против контекста. 1.0 = каждое утверждение подтверждено контекстом; низкое
  значение = модель придумывает факты, которых нет в источнике.

- **answer_correctness** (`FactualCorrectness`, `mode="recall"`) —
  **не путать с "покрытием эталона ответом"**, хотя название режима на это
  намекает. По исходнику ragas (`_factual_correctness.py`,
  `_single_turn_ascore`): `tp` (числитель) в ЛЮБОМ режиме считается только
  по precision-направлению — утверждения из **ответа**, проверенные NLI
  против **эталона**. `recall` лишь добавляет в знаменатель `fn` из
  обратной проверки (утверждения эталона, не найденные в ответе), но не
  заменяет сам `tp`. Итог: ответ, который полностью покрывает эталон, но
  добавляет любую деталь, отсутствующую в (часто лаконичном) эталоне
  дословно, всё ещё может получить 0 — `tp` обнулится на precision-проверке
  независимо от того, что покажет обратное направление. Дефолтный
  `mode="f1"` строже (туда ещё примешивается `fp`), но страдает тем же
  самым — обнулял ~40% строк на полном прогоне. Оставили `recall` как
  наименее плохой из встроенных режимов ragas, а не как честную метрику
  покрытия. Подробности — в docstring в начале `ragas_judge.py`.
  **Перед выводами по конкретной строке смотри
  `reasoning_trace.answer_correctness` в файле прогона
  `logs/judge_trace_log_<timestamp>.jsonl`** — низкая оценка не всегда
  значит фактическую ошибку.

- **answer_relevancy** (`ResponseRelevancy`, `strictness=1` — не ragas-дефолт,
  см. ниже) — отвечает ли ответ по существу заданного вопроса, **независимо
  от фактической верности**. Механика другая, чем у остальных метрик:
  judge-модель генерирует гипотетический вопрос, на который мог бы отвечать
  данный ответ, затем он сравнивается с реальным вопросом через
  **embeddings** (косинусная близость) — не через NLI-вердикт. Единственная
  метрика, которой не хватает просто judge LLM — нужен ещё эмбеддер
  (`JUDGE_EMBEDDING_MODEL`), но он считается **локально**
  (sentence-transformers, без API-вызова и без дополнительных денег — см.
  "Конфигурация" ниже). Непрерывное значение 0..1, не бинарная.

  **Почему `strictness=1`, а не ragas-дефолт 3 — подтверждённая причина, не
  догадка.** Дефолт просит у judge-модели 3 генерации за один вызов (`n=3`).
  На smoke-тесте это давало `TimeoutError` на части строк, и сначала
  выглядело как сетевая нестабильность — увеличение `RunConfig.timeout`
  (180→300) и `max_retries` (10→15) не помогло, ошибка воспроизводилась на
  тех же строках снова. Проверили вызов к Yandex напрямую, в обход ragas, с
  тем же текстом и `n=3` — Yandex сразу отвечает `400 Bad Request`:
  *"When n > 1, temperature must be greater than 0"*. Наш judge LLM работает
  на `temperature=0` глобально (ради воспроизводимости остальных 4 метрик),
  так что `n=3` при `temperature=0` — это **гарантированный отказ**, не
  временный сбой. ragas ловит любое исключение и ретраит с экспоненциальным
  бэкоффом (до 60 сек между попытками) — 400 повторяется на каждой попытке
  identично, и когда суммарное время ретраев превышает `RunConfig.timeout`,
  наружу вылетает `TimeoutError`, маскируя настоящую причину. Больше
  ретраев/времени эту ошибку принципиально не чинят — `strictness=1` просто
  не отправляет несовместимый запрос.

  **Отдельная, всё ещё не решённая проблема — ложные `noncommittal`.**
  Если сгенерированный вопрос помечен моделью как `noncommittal` (уклончивый,
  расплывчатый), итоговый score = 0 **независимо от косинусного сходства**.
  На полном прогоне (81 строка, до фикса выше) это дало 25 нулей (31%), из
  них только 7 — реальные "в документах нет ответа" случаи (там 0 логично).
  Остальные ~18 — судя по всему, ложные срабатывания на **коротких, но
  прямых и верных** ответах (пример: вопрос "Применяется ли хирургическое
  лечение...?", ответ "Не применяется." — `faithfulness=1.0`, полностью
  подтверждён контекстом, но `answer_relevancy=0.0`, потому что judge счёл
  вопрос "Does this rule apply?" уклончивым). Не исправляли — если
  понадобится, вероятно, придётся смотреть в сторону кастомного критерия
  вместо `ResponseRelevancy` для этого конкретного паттерна данных.

- **context_precision** — насколько контекст, который передали модели, был
  реально полезен для данного ответа (нет ли в контексте шума/нерелевантных
  чанков). Низкое значение = ретривер тянет лишнее.

- **context_recall** — насколько эталонный ответ вообще можно вывести из
  переданного контекста. Низкое значение = ретривер не нашёл нужные чанки —
  это ограничение ретривера, а не языковой модели, которая отвечает.

### Как интерпретировать вместе

- Низкий **context_recall** + низкий **faithfulness/answer_correctness** →
  скорее всего проблема ретривера (нужный кусок документа не нашли), а не
  генерации.
- Высокий **context_recall**, но низкий **faithfulness** → контекст был
  нужный, но модель всё равно придумала/исказила факты — проблема генерации.
- Низкий **answer_relevancy** при высоком **faithfulness** → ответ фактически
  верный, но не отвечает на заданный вопрос (ушёл в сторону, многословный,
  или уклончивый) — проверить промпт/инструкции RAG-модели, не ретривер.
- **answer_correctness** = 0 — открыть файл трейса нужного прогона
  (`logs/judge_trace_log_<timestamp>.jsonl`) по этому `id` и посмотреть
  `reasoning_trace.answer_correctness` перед тем, как делать выводы: причина
  не всегда фактическая ошибка. Это по-прежнему частый случай
  и с `mode="recall"` (см. описание метрики выше) — ответ, который по сути
  верен, но многословнее эталона, вполне может получить 0.

## Модули

```
eval/
  run_loader.py        загрузка + валидация run-файла (.parquet/.csv)
  judge/
    base.py             интерфейс Judge (evaluate(df) -> df с колонками метрик)
    ragas_judge.py       RagasJudge — реализация на ragas (дефолтные промпты),
                          учёт токенов/стоимости, логирование трейсов
  report.py              агрегация метрик в отчёт + логи прогонов
scripts/run_eval.py       CLI: run_loader → RagasJudge → report
tests/                    pytest, без сетевых вызовов (метрики мокаются)
verify_setup.py            одноразовый smoke-тест (1 строка, если задан judge)
```

## Конфигурация (`.env`, не в гите)

- `JUDGE_BASE_URL` / `JUDGE_API_KEY` / `JUDGE_MODEL` — любой OpenAI-совместимый
  эндпоинт (сейчас Yandex Cloud AI Studio, `deepseek-v4-flash`).
- `JUDGE_EMBEDDING_MODEL` — опциональна (дефолт
  `intfloat/multilingual-e5-small`), нужна только `answer_relevancy`
  (`ResponseRelevancy`). Считается **локально** через `sentence-transformers`
  (новая зависимость проекта, тянет `torch`/`transformers`), не через
  `JUDGE_BASE_URL` — не расходует деньги/квоту judge-провайдера, не зависит
  от того, есть ли у него embeddings-эндпоинт вообще. При первом вызове
  скачивает модель с HuggingFace Hub (нужен интернет один раз).

  **Почему не `ragas.embeddings.HuggingfaceEmbeddings`** (свой локальный класс
  ragas, казалось бы очевидный выбор): в установленной версии ragas 0.3.9 он
  abstract-incomplete — не реализует `aembed_query`/`aembed_documents`,
  которые требует базовый класс, и падает с `TypeError` при попытке
  создать экземпляр. Вместо этого `_build_default_embeddings` в
  `ragas_judge.py` использует `langchain_huggingface.HuggingFaceEmbeddings`,
  обёрнутый в `ragas.embeddings.LangchainEmbeddingsWrapper` — тот же паттерн,
  что уже был для LLM (`ChatOpenAI` + `LangchainLLMWrapper`). Проверено
  вручную (реальная загрузка модели + `embed_query`/`embed_documents`),
  прежде чем закладывать в код.
- `.env` **не подхватывается автоматически** — нужно `uv run --env-file .env ...`.
- `JUDGE_USAGE_LOG_PATH`, `JUDGE_TRACE_LOG_PATH`, `JUDGE_PRICE_PER_1K_*_TOKENS`,
  `JUDGE_MAX_CONCURRENCY` — опциональные переопределения, см. `.env.example`.
- `JUDGE_TIMEOUT` (дефолт 300) / `JUDGE_MAX_RETRIES` (дефолт 15) — шире
  ragas-дефолтов (180/10) как общий запас прочности под не полностью
  предсказуемого провайдера. Не чинят ничего конкретного сами по себе — тот
  единственный найденный сбой (`answer_relevancy`, см. описание метрики
  выше) оказался детерминированной ошибкой 400 от Yandex, а не тем, что
  лечится увеличением таймаута.
